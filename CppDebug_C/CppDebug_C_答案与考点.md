## 1. Bug ①（易）：减法被实现成加法

**位置**：`expr.cpp` 末尾 `eval()` 的 `switch (op_type)` 中 `case '-'`（约 439 行）。

**改动前（正确）**
```cpp
case '-'    : return val1 - val2;
```
**改动后（故障）**
```cpp
case '-'    : return val1 + val2;
```

**最小复现**
```text
输入: 1-2   期望: -1   实际: 3   (1+2)
输入: 5-3   期望: 2    实际: 8   (5+3)
```

**如何定位**
- 跑 `./build/expression_calculator test` 时，所有含 `-` 的式子大面积 FAIL，且实际值都比正确值**大**（因为 `a-b` 变成了 `a+b`）。
- 在 `eval()` 的 `switch` 里用 `std::cout` 打印 `op_type`、`val1`、`val2` 进入每个分支，立刻能看到 `-` 分支里算的是加法。
- 或直接对 `expr.cpp` 的 `switch` 逐行读：`case '-'` 这一行返回值明显写成了 `val1 + val2`。

**原因与影响范围**
减法运算被错误地返回两数之和。影响**所有包含减法**的表达式，与乘除无关。属于最直观的「运算符执行错误」，适合作为入门突破口。

**修复**：把 `return val1 + val2;` 改回 `return val1 - val2;`。

## 2. Bug ②（中）：乘法被实现成「左操作数平方」

**位置**：`switch (op_type)` 中 `case '*'`（约 440 行）。

**改动前**
```cpp
case '*'    : return val1 * val2;
```
**改动后**
```cpp
case '*'    : return val1 * val1;
```

**最小复现**
```text
输入: 2*3   期望: 6    实际: 4   (2*2)
输入: 3*4   期望: 12   实际: 9   (3*3)
输入: 5*5   期望: 25   实际: 25  (5*5，恰好相等，会掩盖！)
```

**如何定位**
- 含 `*` 的式子大多算错，但 `a*a` 这种平方输入会**恰好正确**，容易让人误以为乘法没问题——排查时要挑 `a≠b` 的乘法用例（如 `2*3`）。
- 在 `case '*'` 分支打印 `val1`、`val2`，会发现返回值只用了 `val1`。
- 直接读 `switch`：`return val1 * val1;` 一眼可辨。

**原因与影响范围**
乘法只取了左操作数平方，丢失了右操作数。影响所有含乘法且两因子不等的表达式。**注意 `a*a` 类用例不报错**，是本题的一个小陷阱。

**修复**：改回 `return val1 * val2;`。

## 3. Bug ③（中）：除法被实现成取余

**位置**：`switch (op_type)` 中 `case '/'` 的最后一句 `return`（约 450 行，位于除零检查与 `INT32_MIN/-1` 特殊处理后）。

**改动前**
```cpp
        return val1 / val2;
```
**改动后**
```cpp
        return val1 % val2;
```

**最小复现**
```text
输入: 7/2   期望: 3    实际: 1   (7%2)
输入: 10/3  期望: 3    实际: 1   (10%3)
输入: 8/4   期望: 2    实际: 0   (8%4)
```

**如何定位**
- 含 `/` 的式子结果都是「除不尽的余数」而不是商，规律非常稳定（实际值 = 期望值的余数）。
- 在 `case '/'` 分支打印 `val1`、`val2`，看返回值来自 `%` 而非 `/`。
- 直接读：分支末尾 `return val1 % val2;` 与上方除零保护、`INT32_MIN/-1` 处理明显不搭。

**原因与影响范围**
除法返回了余数，把「商」算成了「模」。影响所有含除法（且不能整除）的表达式。除零保护、`INT32_MIN/-1` 这两个原有保护**仍然保留**，所以 `1/0` 仍会正确报「除数为零」，不会崩溃——这也提醒：测试认的是 `eval_ok` / 返回值，不是 `std::cerr` 的提示文本。

**修复**：改回 `return val1 / val2;`。

## 4. Bug ④（难）：整数按 16 进制（十六进制）解析

**位置**：`eval()` 的「单数字」分支，把 token 字符串转成整数那一行（约 349 行）。

**改动前**
```cpp
std::int32_t out = static_cast<std::int32_t>(std::strtol(tokens[p].str, nullptr, 10));
```
**改动后**
```cpp
std::int32_t out = static_cast<std::int32_t>(std::strtol(tokens[p].str, nullptr, 16));
```

**最小复现**
```text
输入: 100/1   期望: 100   实际: 256   (0x100)
输入: 11111+1 期望: 11112 实际: 69906 (0x11111 = 69905)
输入: 10+10   期望: 20    实际: 32    (0x10+0x10 = 16+16)
输入: 1+2*3   期望: 7     实际: 7     (全是个位数，16 进制下也正确！)
输入: 1/100   期望: 0     实际: 0     (1/256 整除为 0，也正确！)
```

**如何定位**
- 这是最隐蔽的一处：只要表达式里的数字**全是个位数（0–9）**，`16` 进制和 `10` 进制结果相同，所以 `1+2*3`、`(1+2)*3`、`1-2`、`0/1` 这些简单用例**全部算对**。
- 一旦表达式里出现两位数及以上（如 `100`、`11111`、`10`），`16` 进制的位权立刻放大结果（100→256、10→16），大面积 FAIL。
- 定位要点：**对比「只含个位数的式子」与「含多位数的式子」**——前者全过、后者全错，基本就能锁定是数字解析环节，而不是运算符。
- 在单数字分支打印 `tokens[p].str` 与解析出的 `out`，并对照正确值，会看到 `100` 被读成了 `256`。
- 直接读那一行：`strtol(..., 16)` 的第三个参数被改成了 `16`。

**原因与影响范围**
`strtol` 的进制参数被从 `10` 改成 `16`，所有数字字面量被当成十六进制整数读入。它不依赖任何运算符，所以和上面三处完全独立；也正因为它在「分词→转整数」阶段，运算符层面的排查对它无效（乘法/减法单独修好后，多位数用例仍错），必须回到数字解析这一行。

**修复**：把 `16` 改回 `10`。

## 5. 禁止的绕过方式（判分时直接不及格/扣分）

- ❌ 改 `test` 文件的期望值或删除测试行（改测试数据）。
- ❌ 在 `eval()` 里对特定输入硬编码返回值（如 `if (expression == "100/1") return 100;`）。
- ❌ 只改 `std::cerr` 提示字符串冒充修复（测试不认 stderr 文本，认 `eval_ok`/返回值）。
- ❌ 把 `expr.cpp` 之外文件（尤其 `main.cpp`）改来让测试通过。

## 7. 环境提醒（务必先读）

1. **这套题必须在 Linux 上编译运行**：项目依赖 POSIX `<regex.h>`、`mkstemp()`、`popen()`、`/tmp` 等，Windows / MinGW 编不过。（可装 VMware+Ubuntu、学校服务器、云主机或 ROS2 容器。）
2. **源码保持 UTF-8**：Linux g++ 默认按 UTF-8 读源文件，GBK 会带来「题目之外」的编译错误。你本机用 Dev-C++ 打开中文注释会乱码，用 VS Code 看即可；若非要看 GBK，用
   `iconv -f UTF-8 -t GBK expr.cpp > expr_gbk.cpp` 生成**只读副本**，不要替换、不要提交 `expr.cpp`。
3. **做题前先 `rm -rf build`**：增量构建不会删旧产物；上一轮残留的 `build/` 可能掩盖重新编译的问题。
