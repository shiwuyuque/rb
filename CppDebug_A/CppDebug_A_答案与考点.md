## 3. 逐处详解

### ① `case '*'` 写成加法（易）

**复现**：交互模式输入 `2*3`，得到 5；`2+3*4` 得到 9。

**定位**：`eval()` 的 trace 会打印 `eval(0, 2) : 2 * 3 `，说明分词和根节点选择都正常，错误只可能发生在最后的 `switch (op_type)`。直接看 `case '*'` 那一行即可。

**原因与影响范围**：`return val1 + val2;` 把乘法当加法。所有含 `*` 的表达式都错，而且乘法常出现在子表达式里，错误结果会继续参与外层运算（例如 `2+3*4` 不是只差一点，而是 14 → 9）。**影响范围不是「乘法那一题」，是所有含乘法的树。**

**修复**
```diff
-      case '*'    : return val1 + val2;
+      case '*'    : return val1 * val2;
```

---

### ② `case '-'` 左右操作数颠倒（易）

**复现**：`5-2` → -3；`10-3-2` → 9。

**定位**：`5-2` 的绝对值和期望一样、符号相反，先怀疑减法方向。在 `case '-'` 前加一句 `std::cout << val1 << " " << val2 << std::endl;` 或用 gdb 在 `switch` 处下断点，能看到传进来的 `val1=5, val2=2`，但返回 `2-5`。

**原因与影响范围**：`val1` 是根运算符左边的值、`val2` 是右边的值，减法不满足交换律。写成 `val2 - val1` 后，**每一层减法都反号**，`10-3-2` 会连锁放大成 9。另外它会改变中间结果，可能间接让除法的分子/分母变化——排查时要意识到「一处运算错误会污染上层」。

**修复**
```diff
-      case '-'    : return val2 - val1;
+      case '-'    : return val1 - val2;
```

---

### ③ 优先级判断漏掉 `'/'`（中）

**复现**：`8/2` → `invalid expression`，stderr 是「表达式错误：缺少运算符」。README 给的示例里就有 `100/1`、`1/100`，一跑就中。

**定位**：
- `eval(0, 2) : 8 / 2 ` 说明 token 都在、`/` 也被正确分词了；
- 但 `op_type == 0` 被触发 → 说明**扫描根节点时没把 `/` 当成可选运算符**；
- 顺藤往上看 `current_level` 的赋值：`} else if (tokens[i].type == '*')`，只处理了 `*`。

**原因与影响范围**：`current_level` 为 0 的 token 不会被选为根节点。`/` 被漏掉后，任何含除法的区间都找不到合法顶层运算符，报「缺少运算符」并置 `eval_ok = false`。**括号包裹也救不了**（`check_parentheses()` 剥掉外层后里面还是除法），所以全部含 `/` 的表达式都失效，共 312/1000 条。

注意这与 `case '/'` 无关：`case '/'` 的代码是对的，只是**永远走不到**。这是最能体现「要理解影响范围而不是改到某条测试通过」的一处。

**修复**
```diff
-        } else if (tokens[i].type == '*') {
-          current_level = 2;  //* 优先级高于+-，低于括号
+        } else if (tokens[i].type == '*' || tokens[i].type == '/') {
+          current_level = 2;  //*/优先级高于+-，低于括号
         }
```

---

### ④ 除零判断多加了 `val2 < 0`（难）

**复现**：`8/(0-2)` → `invalid expression`，stderr 打印「表达式错误：除数为零」，但除数明明是 `-2`；对照 `8/2` → 4 正常。

**定位**：
- 1000 条批量测试里只有 38 条失败，且失败的全是「除数为负」的式子 → 先按表达式特征分组，而不是逐条看；
- 用交互模式单跑 `8/(0-2)`，trace 显示左右子式都算对了（`0-2` = -2），却在 `case '/'` 里失败 → 聚焦到 `if (val2 == 0 || val2 < 0)`；
- 提示文本是「除数为零」，但条件里多了一个 `val2 < 0`。**提示只是 stderr 输出，真正决定测试成败的是 `eval_ok` / `success` 和返回值**——把提示文字改掉不会让测试通过，这是常见误区。

**原因与影响范围**：README 明确要求「接受复合计算过程中的负数结果」「除零和非法表达式应保持现有错误处理行为」。这里把「除数为负」误当成错误，凡右操作数为负（含 `(0-2)` 这类复合结果）的除法都被拒绝。原 `val2 == 0` 保护仍在，所以 `1/0` 依然安全报错，不会 SIGFPE；生成器也会跳过除零用例，批量测试不会崩。

**修复**
```diff
-        if (val2 == 0 || val2 < 0) {
+        if (val2 == 0) {
```

## 4. 新手排查流程（50 min 版）

```bash
cd CppDebug_A
make
./build/expression_generator 1000 > test     # 或直接用仓库自带的 test
./build/expression_calculator test 2>/dev/null | head -40
```

1. **先看 FAIL 的形状**：把失败表达式按「含 `*` / 含 `-` / 含 `/` / 除数为负」分组，不要一条条硬啃。
2. **挑最短的 FAIL 单跑**，交互模式会打印 `eval(p, q)` 递归轨迹，用来判断「分词对不对 → 根节点选得对不对 → 最后的运算对不对」：
   ```bash
   ./build/expression_calculator
   Please input the expression: 2*3
   ```
3. **按推荐顺序修，每修一处就重跑一次**，记录通过数：
   `550 → 608（③）→ 705（①）→ 962（②）→ 1000（④）`
   先修让表达式「直接非法」的 ③，再修结果错的 ①②，最后收拾只剩几十条 FAIL 的 ④。
4. **全过后再跑手工边界用例**（不要只信 `All tests passed!`）：
   ```bash
   cat > mytest <<'EOF'
   6 2*3
   14 2+3*4
   3 5-2
   5 10-3-2
   4 8/2
   5 8/2+1
   -4 8/(0-2)
   4 (0-8)/(0-2)
   EOF
   ./build/expression_calculator mytest
   ```
5. 也可以用 `printf` / `cout` 在 `switch (op_type)` 前打印 `val1`、`val2`、`op_type`，或用 gdb 在 `eval()` 下断点看递归区间，作为「复现错误」的过程证据。

## 7. 评分要点（对齐 README）

- **按 Bug 点给分，难度决定分值**（建议）：① 15 / ② 15 / ③ 25 / ④ 45，合计 100。
- **过程分**：每处都要能说出「复现输入 → 用了什么手段（trace / cout / gdb / 分组统计）→ 定位到哪一段 → 为什么错 → 影响哪些表达式 → 怎么修」，而不是「我改了一行测试就过了」。
  - ③ 必须能说出「`case '/'` 没错，是根节点扫描漏了 `/`，所以所有除法都走不到运算」；
  - ④ 必须能说出「提示文字不是判定依据，`eval_ok` / `success` 才是」。
- **未修完也要给过程分**。记录模板：
  | Bug | 复现输入 | 期望 / 实际 | 定位依据（命令 / trace 行） | 当前结论 | 是否已修 |
  | --- | --- | --- | --- | --- | --- |
- **禁止的绕过**：修改 `test` 里的期望答案、删除测试行、对样例做特判、硬编码输出、把错误提示字符串改掉冒充修复、改动 `main.cpp` / `expr.hpp` / `Makefile` 并作为答案提交（这些文件允许临时改来调试，但提交前要恢复原样）。
